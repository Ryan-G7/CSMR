# CarAR 系统代码审查（2026-10-20）

审查范围为实际应用工程 `CarAR` 的全部自有 C# 运行时代码、场景生成与构建代码、HJXR / OpenXR 接口，以及启动和模型处理脚本。核对了本地 MRTK / XRI 中与选择、约束和释放有关的实现；没有对第三方 SDK、Unity 引擎或全部第三方包作全面审计。根目录 Unity 工程不是当前应用入口。

目前是具备整车展示和交互的 MR 原型：车辆摆放、停车锁定、独立门盖、爆炸还原、手柄控制及设备校准链路已经存在。还不能将其作为已经完成空间精度和评审业务验收的系统。尤其不能用车辆根坐标不变或 SDK 请求成功，代替实体对齐精度的验收。

## 本次确认并修复的问题

| 优先级 | 问题与影响 | 修复与验证 |
| --- | --- | --- |
| P1 | 定位板校准等待期间仍可从面板解锁、爆炸、精调或重新摆放。原厂异步改变输入坐标时，这些操作可能使用前后不同的坐标基准。 | 校准期间限制整车变换、解锁和摆放，校准入口主动取消摆放并锁车；回归验证多个操作入口都保持原停车位置和地面高度。 |
| P1 | K 键直接调用原生校准入口，绕过面板的锁车、取消摆放和动画检查。 | 键盘与面板共用校准入口，实际提交方法也检查爆炸状态并执行锁车；组装完成后再校准。 |
| P1 | 日志无法打开时仍提交 WorldSync；原厂可能已经对齐渲染，而应用拿不到用于同步输入的结果。 | 在提交原生命令前检查反馈日志可读性，读取中断或日志被截断时立即要求重启；验证真实文件追加读取和独占锁定文件。 |
| P1 | 已放置车辆的 PlaceAt 在估计地面分支忽略新的 X/Z；另一个分支会重新测量打开/展开后的包围盒，改变既有地面支点。 | 后续所有放置保留已建立的根对象与地面的高度差，并完整应用目标位置；验证连续估计、手动、跟踪地面放置及车门打开时的支点。 |
| P2 | 摆放期间切换到另一只已按住扳机的手柄，会沿用上一只手柄的释放状态，从而意外确认。 | 每次跟踪手柄变更都重新等待该手柄释放扳机；使用真实 Input System 事件模拟右手丢失跟踪、左手按住扳机接管。 |
| P2 | 禁用输入组件后，位于 XR Origin 下的射线和握持对象仍然活动；销毁组件也未清理这些对象。 | 启停时同步管理输入动作、事件订阅、摆放预览和手柄对象，销毁时清理组件创建的对象；验证禁用与重新启用。 |
| P2 | 测光数据失效后，状态显示大厅预设，实际光照仍保持最后一次实时数据。手动方向和自动模式切换也会残留旧球谐环境光。 | 断流后恢复预设的强度、颜色、方向和环境光；切换模式清除旧数据，自动模式等待新帧；用模拟提供者验证实际 Light 与 RenderSettings。 |
| P2 | 非法颜色、方向或球谐系数可以污染渲染；刚体矩阵校验没有覆盖所有平移元素。 | 验证光照提供者数据的有限性，在 OpenXR 输入变换入口再次检查完整有限刚体矩阵；覆盖 NaN 颜色和平移。 |
| P2 | Setup 默认切换到 Android，与当前 Windows / Pimax / HJXR 的实际部署不一致；忽略保存场景对话框的取消结果。 | 默认 Windows 64 位，取消时不执行 Setup；场景替换前尊重取消，构建与 Setup 复用播放器设置代码。 |
| P2 | 自动首次摆放可与用户正在进行的手动摆放预览竞争；重放置可能保留过时的“手动地面”状态。 | 手动预览期间暂停自动首次摆放，每次 PlaceAt 重新设置地面来源状态。 |

清理了未使用的“标记作为地面”分支、车辆标记偏移字段、门盖立即重置方法和无参数 SDK 命令包装。竖直定位板只用于坐标对齐，地面仍需独立确认。新增忽略本地检查依赖和 Python 字节码；工作区原有暂存缓存及用户模型修改没有纳入本次提交。

## 结构与质量判断

车辆、摆放、输入、UI、光照和原生接口已有独立组件，继续使用 Unity / MRTK / XRI 负责姿态、交互和约束的方向合理。本次优先修复跨组件状态约束，没有另建一套交互或跟踪框架。

后续质量工作的重点是明确应用状态与评审数据模型。当前 UI 仍依赖按钮数字索引，CarShowroom 还包含较多诊断和冒烟测试代码，HJXR 反馈依赖厂商日志格式；这些均是维护成本。若菜单继续扩展，应引入具名动作绑定；测试宜逐步进入独立测试程序集，原生完成反馈优先改用厂家正式支持的接口。当前 SDK 中未实现的 getter 不能作为替代方案。

模型约 131 万三角形，存在大量分件和 MeshCollider；4096 阴影、SSAO、反射探针及双眼渲染的实际成本需要在目标头显上剖析。没有充分依据直接删除几何、替换精确碰撞或声称满足所有场景的帧率要求。

## 完整汽车 MR 评审仍缺少的能力

1. **可重复的空间验收。** 记录实体定位板重合误差、车辆与地面的误差、不同距离/视角下的偏差，测试走动、遮挡、跟踪丢失与恢复。当前设备链路没有已建立的跨会话持久锚点方案；不能声称重启后能恢复同一大厅位置。
2. **评审任务与记录。** 缺少项目/车型/版本、评审人员、检查项、问题等级、结论、批注/截图和导出报告的数据结构与持久化。当前 UI 中的 ConfirmedCount 是按钮诊断计数，不是评审记录。
3. **工程测量。** 缺少带单位和精度说明的尺寸、间隙、面差等测量工具，以及测量结果与模型版本的关联。模型 1:1 当前指源模型单位，尚无原厂尺寸标定；爆炸图是展示动画，不能作为装配过程或机构干涉计算。
4. **运行异常闭环。** 需要可供评审者理解的设备断连、定位失效、恢复/重新标定流程及会话保存。启动脚本的相机恢复不能替代运行中整个会话的恢复策略。
5. **可迁移构建与性能基线。** MRTK 为仓库内本地包，迁移时必须保留依赖目录。正式交付前建立固定设备、运行时和 SDK 版本、性能采样与发布构建流程，记录兼容补丁的上游版本。

这些是仍待实现或验收的能力，不列入“已修复”。

## 自动验证

Unity 版本为 6000.6.3f1，构建入口为 `CarAR.EditorTools.CarARSetupWizard.BuildPreview`，运行入口为 Windows 播放器的 `--carar-smoke`。构建期间执行 ABI、坐标手性、原生结果回放、旧结果过滤和跨午夜时间戳检查。运行期间执行 MRTK、真实 Input System 手柄事件、车辆动画和本次新增回归测试。

日志为工程目录下的 `review-build.log` 和 `review-smoke.log`。只有日志中的 PASS 和进程退出码 0 才表示自动检查通过。自动检查不覆盖真实视频、头显最终合成或物理板精度，也未重导出用户正在修改的 AMG.blend。

本次结果：Windows 构建退出码 **0**；MRTK、Input System 手柄、新增状态回归和整车动画四组运行验证全部 PASS，播放器退出码 **0**，覆盖 145 个渲染部件和四处门盖。PowerShell 启动/调参脚本解析及 7 个 Python 工具的语法检查通过。首轮新增测光测试的夹具缺少相机引用，补齐后重新构建并通过完整测试。

构建退出时仍有 Unity JobTempAlloc 释放警告；两份此前构建日志也有同样警告，尚未归因到具体引擎或包代码。本次没有据此宣称内存泄漏审计通过。
